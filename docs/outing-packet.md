# Canonical outing packet (P3.14)

The new packet is nested in the existing owned EventPlan JSON. No second itinerary model, calendar identity, database migration or worker is added. P3.13's reviewed disruption contract is included but remains inactive. All executable outing examples use the existing explicit rehearsal provider and fictional selected contacts. Existing plans without an outing retain their prior behavior.

## User path

Open Event plans, choose a fictional session/attendees, and use the restaurant component first if a table should anchor dinner. Build the whole outing: each selected person chooses an example origin, outward and return mode, estimates, handling/storage, and fare estimate. Cycle, PT, bike + train, Uber/rideshare and driving are available. Car and bicycle return constraints reject stranded-vehicle proposals. The first version uses public station examples only; the confirmed private household origin is not a default or fixture. The inherited discovery planner still provides explicit origin handoffs and the actual household cycling lookup remains private operator evidence.

Meal allowances without a selected table and optional drinks without a venue stay visibly unselected. A chosen table contributes its exact branch, address, start/end and current reservation state; it must fit the event buffer. Venue connection, train/tram transfers, last services, weather, storage, fares and live availability are unverified. Maps URLs are supported explicit browser handoffs, not route API results. In this rehearsal they target a labelled public example meeting point, not the fictional venue. Bike + train links require separate cycle and transit checks and do not prove bicycle carriage. No fare is a live rideshare quote or booking.

The master calendar interval spans the earliest participant departure to latest return. It includes meal, transfer, arrival, event, optional drink, return and handling allowances. The event anchor retains its source start/end/timezone separately; doors remain unknown. Rebuilding revises the existing CalendarHandoff UID and description, invalidating prior calendar commands; it never creates a second busy block. One collective occupied interval is used for all invitees, so a later-departing person sees a wider block than their own private travel supplement.

## Sharing and ticket boundaries

An invitation's common calendar description is visible to all attendees. It never includes private origins, participant-specific map links, booking references, mailboxes or ticket QR/barcodes. There is no claim that Google supports a different shared description per guest. Addressed email packets add only that person's travel and authorized ticket metadata. The owner packet additionally contains order and cancellation information. Email and calendar invitations are separately approved actions; RSVP remains unknown.

CalendarHandoff schema 2 adds a bounded shared description; schema 1 restores unchanged and retains its historical approval digests. Full packet changes are bound into the description by an opaque fingerprint. The existing event-plan version/nonce/CAS gates cover every mutation. No hidden state is accepted from browser forms.

`ticket_documents` is a trusted server-side issuer-adapter seam, not a browser form or a file upload. An eligible PDF record needs an exact confirmed order, issuer-verification evidence, exact audience, filename, application/pdf MIME, bounded positive size, SHA-256, HTTPS issuer/secure link and future expiry. The builder filters unavailable, expired, unverified, mismatched or other-recipient records. It never generates PDF bytes, ticket barcodes or Wallet passes, and never retrieves a URL. Currently no real issuer ingestion/storage/attachment adapter is connected; the runnable preview correctly says tickets unavailable. Synthetic metadata exists only in tests to exercise redaction and stale-link approval. Actual link ACLs and issuer authenticity must be verified by the future adapter, not inferred from an HTTPS URL or filename.

## Delivery, changes and reconciliation

Calendar commands still use the existing CalendarHandoff and RehearsalProvider. After confirmed booking and owner master-calendar evidence, each addressed email has a displayed payload digest and exact mailbox. Its request key and unknown receipt commit before the adapter call. A repeated form or fresh click for the same payload cannot dispatch again. Failure is retained; unknown can only query the original request key. Exceptions, incorrect evidence and CAS conflicts leave unknown. Reconciliation is available after the general action cap. Unknown calendar/email delivery blocks route revisions or organizer changes until resolved.

Restaurant, quote, ticket-document or source changes make the stored packet stale; calendar/email actions then require rebuild. Organizer reschedule/cancellation retains purchase receipts, canonical calendar identity and private source anchor, and rebuilds the packet for a new approval. Cancellation never claims a ticket refund or restaurant cancellation. Already delivered packets are updated through the same identity and separately approved recipient commands. Shared calendar changes and private email changes are not silently sent.

## Live activation steps — not completed

1. Select a real dated outing, exact session/venue, participant identities, origins and permissible map/source use. Resolve owner calendar/mailbox and friend recipients explicitly. Inspect actual source/booking/ticket evidence; no rehearsal may be relabelled live.
2. Choose an orchestration route. The assistant currently has Gmail and Google Calendar tool capabilities (metadata discovery only in this increment); those connections do not provide credentials to Omarchy. A backend integration needs a separately approved OAuth client/grant, private token storage, calendar write and email-send scopes, and a way to reconcile uncertain sends. No tokens are copied from browser or root connectors.
3. Bind a deterministic provider event ID to the existing UID, use one master event, read-back/ETag reconciliation on updates, and selected invitation notifications. Do not duplicate the owner's busy block or use direct writes to friends' calendars. Gmail delivery must produce bound provider evidence; a local key alone cannot guarantee server-side email idempotency.
4. For actual PDFs, obtain authorized provider files or secure links and verify recipient access. Calendar attachment support requires the provider's attachment capability and access checks; never publish private tickets into the common event. Gmail MIME attachments require actual verified bytes. Until then show the secure link/metadata only, without claiming an attachment was sent.
5. Connect tested live journey/disruption normalization, durable scheduler/current-owned-plan lookup and selected notification channel independently. PTV key-request email is pending with the parent; this increment sends none. No watch is scheduled without a saved dated journey.

## Review and demonstration

Run focused labels `shelf.tests.test_outing_packet`, `shelf.tests.test_event_plans`, `shelf.tests.test_calendar_handoff`, `shelf.tests.test_calendar_recipients`, `shelf.tests.test_restaurant_plans`, plus P3.13 transport regressions. `scripts/demo_outing_packet.py ${PRIVATE_RUNTIME_PATH}` replays actual HTTP views in a transient test DB and renders five static review pages: whole outing, uncertain email, reconciliation, changed route awaiting approval, cancellation. No external services are invoked. Use the existing full-suite and independent V/Q gates before promotion. Deploy with the existing controller lock, exact old/new source manifests, no migrations, preserved private data/keys and unchanged expiry. CalendarHandoff schema 2 is backward-readable by this build, but older P3.12.1/P3.13 code cannot read new outing calendar records. Automatic source rollback is therefore allowed only while the whole logical database still matches its pre-promotion baseline. If any user write occurred, the deployment helper must refuse the old-reader downgrade, preserve current source/data and report FORWARD_RECOVERY_REQUIRED for repair-forward. Never restore an old database over new receipts. After users create outing packets, a later downgrade needs a separately tested compatible reader; it is not a supported source-only rollback.
