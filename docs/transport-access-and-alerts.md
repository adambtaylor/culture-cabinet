## Exact live-access requirements

The official PTV Timetable API requires a developer ID and API key, and a per-request HMAC signature. Its published registration instructions ask the account owner to email APIKeyRequest@ptv.vic.gov.au with subject `PTV Timetable API – request for key`; credentials arrive by email and the sender is added to API notices. No email, subscription, key request or credential installation has occurred. Source: https://www.vic.gov.au/public-transport-timetable-api and its linked API key/signature document. Store a subsequently approved key privately in the existing provider-secret pattern; never in query logs or source. This API provides timetable/departure and disruption data, not the Journey Planner's fully assembled itineraries. Full journey transfer rules remain a separate responsibility.

The separate GTFS Realtime service requires an Open Data subscription key. Its collection page calls the header `KeyID`; the current Metro service-alert OpenAPI document specifies `Ocp-Apim-Subscription-Key`. The collection page says newer replacement-bus information was added, but the endpoint document says replacement buses/deviations/platforms are excluded. These discrepancies must be resolved with the provider and a real approved key before asserting complete replacement-bus coverage. Do not choose a header or silently promise comprehensive coverage. Official sources: https://opendata.transport.vic.gov.au/dataset/gtfs-realtime and its Metro Train service-alert resource.

Static GTFS Schedule is publicly downloadable (about 248 MB, weekly, rolling 30 days). It can support planned departures, service calendars and shape data, but cannot establish current disruptions or live last-service changes. Its complete feed is unnecessary for this small key-blocked increment. Source: https://opendata.transport.vic.gov.au/dataset/gtfs-schedule . Night services may cross midnight; a last service must be derived for the selected service date/direction and exceptions, not assumed from the final displayed clock time.

Useful public fallback: https://transport.vic.gov.au/journey , https://transport.vic.gov.au/route/timetable/15/upfield-line and https://transport.vic.gov.au/disruptions/disruptions-information . These are normal user/browser pages. Their internal signed URLs are not a supported backend API. No site block, login, paywall or CAPTCHA is bypassed.

## Alert contract and activation boundary

`transport_watch.py` is a pure domain evaluator plus testable scheduling/delivery interfaces. It is NOT a connected feed, durable worker, model, task automation or notification channel. The ordinary evening UI only previews the two check windows and states explicitly that no watch exists. Current EventPlan owns canonical identity/version; a future saved real journey must be resolved from that owned plan. Rehearsal EventPlans cannot be presented as real saved journeys. No new persistent parallel itinerary store is introduced.

For each owned saved/confirmed public-transport leg, the schedule begins departure minus two hours (immediately if saved inside that window), repeats at a proposed five-minute cadence and stops at departure. Return has its own window. A scheduler must atomically replace jobs for the same journey on changes/cancellation, and load the current owned version before every tick; stale jobs must not evaluate or send. No actual journey date or notification recipient has been selected, so no runtime jobs are registered.

Normalised source notices must retain provider-scoped route/stop/trip identifiers, an effective interval, planned/live/unknown status, consequence and official source link. The adapter must mark coverage incomplete for unavailable, stale, truncated, unrecognised or unsupported data, including unresolved service identities. It must not fabricate exact identifiers from display names. Matching is restricted to relevant identities and travel interval. A full-size bicycle plus a metropolitan replacement-bus notice produces explicit bike advice; it never claims a newly safe or available alternative.

Consecutive unchanged notices are suppressed even if retrieval time changes. Material transitions get new occurrence keys, including A → B → A and recurrence after withdrawal/recovery. Each evaluation retires withdrawn or superseded pending occurrences; sent and unknown receipts remain intact for reconciliation. Only current eligible occurrences checked within five minutes can dispatch. Each alert carries the affected leg, source observation/check time, consequence and practical replan action. Unsupported coverage is an unavailable notice, not all-clear. A 200-receipt budget bounds state. No current API can be described as covering every real-world disruption merely because it returns an empty array.

Before transmission the runtime must persist an unknown receipt using the existing owned compare-and-swap pattern; a storage conflict prevents send. A crash/timeout remains unknown, and read-only lookup reconciles it without blind resend. The contract blocks cancelled/changed journeys and sends outside the leg's two-hour window. Only the journey owner is targeted by this layer; friend notification requires its own explicit selection. Tests use fake adapters and ephemeral state. The live data parser, durable CAS adapter, scheduler and actual delivery proof remain external/integration work; this candidate does not claim live notifications.
